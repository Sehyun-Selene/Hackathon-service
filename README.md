# 해커톤 음식 주문 & 코치 호출 서비스

PRD(`해커톤_주문_호출_서비스_PRD.md`) 기반 구현. **두 개의 완전히 독립된 웹 앱**으로 구성됩니다.

```
해커톤 티오더/
├─ participant-app/   참가자용 모바일 웹 (QR 스캔 → 주문/호출)  — 독립 프로젝트
├─ admin-app/         운영진(관리자)용 웹 (주문 현황/호출 처리) — 독립 프로젝트
├─ shared-api/        두 앱이 공유하는 초경량 KV API (의존성 없음) — 실제 배포 시 필요
├─ preview-server.js  로컬 연동 테스트용 정적 서버 (의존성 없음)
└─ README.md
```

두 앱은 코드/빌드/배포가 완전히 분리되어 있고, **오직 공유 데이터 저장소를 통해서만** 간접적으로 연동됩니다 (직접 API 호출 없음).

> ⚠️ **아티팩트 shared storage 관련 정정**: 처음엔 PRD 3.3의 "Claude 아티팩트 영속 저장소(window.storage, shared 모드)"를 그대로 쓰려 했으나, 실제로 아티팩트를 발행해 검증한 결과 이 환경에는 `window.storage` API 자체가 없었습니다 (지원 capability 목록에 storage 없음 — downloads/mcp/self만 있음). 그래서 `shared-api/`라는 초소형 API 서버를 대신 두었고, 키 설계(3.3)는 그대로 유지했습니다.

## 🗄️ 공유 저장소 & 키 설계 (PRD 3.3)

`src/lib/storage.js` 어댑터가 저장소를 추상화합니다.

- **`API_BASE_URL`이 설정된 경우**: `shared-api/`(작은 공유 KV 서버)를 호출 — 참가자/관리자 앱이 서로 다른 배포 URL(다른 origin)이어도 실제로 데이터가 공유됨. **실제 행사 배포 시 반드시 이 방식을 사용하세요.**
- **비어 있는 경우**: `localStorage` 폴백 (`hackathon-torder:` 접두사) — 같은 브라우저 안에서만 유효. 로컬 개발/시연용으로만 사용 (실제 참가자 500명은 각자 다른 기기라 이 모드로는 연동되지 않음).

| 키 | 내용 | 쓰는 쪽 |
|---|---|---|
| `team:{teamId}` | 팀 정보(인원수·알러지) | 참가자(등록) |
| `team-roster` | 등록된 팀 id 목록 (관리자 열거용) | 참가자 |
| `order:{teamId}` | 팀의 식사별 주문 내역 | 참가자 |
| `call:{teamId}` | 호출 목록(사유/상태/타임스탬프/담당코치) | 참가자(생성), 관리자(상태 변경) |
| `call-count:{teamId}` | 누적 호출 횟수 (제한 검증) | 참가자 |
| `coach-roster` | 등록 코치 목록 `{coaches: [{id, name, groupId, group}]}` | 코치(관리자 앱) |
| `soldout` | 품절 메뉴 map | 관리자 |
| `alert-state` | 슬랙 알림 발송 이력 (중복 발송 방지) | 공유 API 서버 |

팀별 키 분리로 동시 쓰기 충돌을 최소화합니다.

## 👥 팀 등록 흐름 (공통 QR)

모든 팀이 **같은 QR/URL**을 씁니다. 참가자가 처음 접속하면 팀 정보를 직접 입력합니다.

1. QR 스캔 → 팀 등록 화면 (팀 번호 · 인원수 · 알러지) — 계열사는 선택하지 않음
2. 입력 후 시작 → 이 기기에 팀 정보가 기억되어 재접속 시 바로 주문 화면
3. 같은 팀원은 **같은 팀 번호**를 선택 (이미 등록된 번호면 정보가 자동 채워짐)

- **음식 주문**은 등록한 **인원수만큼만** 담을 수 있음 (음료는 제한 없음)
- **알러지**는 미리 대응 메뉴를 두는 게 아니라, 수집된 현황을 **관리자가 주문현황 탭의 "알러지" 패널에서 확인**해 케이터링 대체 메뉴를 준비하는 용도
  - **사람 단위로 구분 입력**: "인원 추가" 블록마다 한 사람의 알러지를 모아 선택 → 1명이 여러 개인지, 여러 명이 각각 하나씩인지가 그대로 구분되어 저장됨 (`team.allergies = [[사람1 알러지...], [사람2 알러지...]]`). 관리자 화면엔 "1인(땅콩·견과류), 2인(우유)"처럼 표시되어 대체 메뉴를 몇 개·어떤 조합으로 준비할지 바로 판단 가능

## 🧑‍🏫 코치 담당 구조 (팀 번호 기준 개인별 배정)

계열사 대신, **팀 번호로 코치 개인을 배정**합니다. `config.COACH_ASSIGNMENTS`에 코치별로 이름과 담당 팀 번호를 채워두면(예: `{ name: '김민준', teamNumbers: [1, 2, 3] }`), 그 팀들의 호출은 그 코치가 우선 응답합니다. **지금은 이름·팀 번호 둘 다 비어 있어(TBD) 전부 미배정 상태** — 코치 명단과 팀 편성이 확정되면 값만 채우면 됩니다.

- 관리자 입장 화면: 이름이 확정된 코치는 목록에서 **선택**, 아직 명단에 없으면 **직접 입력** (PRD 5.1 "선택 또는 입력")
- 참가자 화면엔 자기 팀 번호를 담당하는 코치가 있으면 "OOO 코치가 담당합니다"로 안내, 없으면(TBD 상태) 일반 안내 문구만 표시
- 호출 알림에서 내가 담당하는 팀의 호출이 상단에 강조 표시되고, "내 담당 팀만" 필터 제공
- **코치 현황 탭**: 코치 개인별 리스트 + 상태(🟢 대기 / 🔴 팀 XX 대응 중) + 본인 담당 팀의 대기 호출 수. 담당 코치가 바쁘면 다른 코치가 대신 처리하도록 판단하는 용도
- 어떤 사유로 호출하든 예외 없이 팀당 누적 호출 횟수(5회)에서 일괄 차감됩니다.
  - ※ 실내 GPS 정확도 한계 때문에 위치 지도 방식은 사용하지 않고, 이 코치 현황 리스트로 대체했습니다.

## 🚀 실제 배포 순서 (행사에서 실제로 쓰려면 이 순서대로)

### 1) 공유 API 서버 배포 (Render 기준)

1. [render.com](https://render.com) 가입 → New → Web Service
2. 이 저장소의 `shared-api` 폴더를 연결 (Root Directory: `shared-api`)
3. Build Command: 비워둠 / Start Command: `node server.js`
4. 배포 후 발급되는 주소 확인 (예: `https://hackathon-torder-api.onrender.com`)
5. `https://<그 주소>/health` 접속해서 `{"ok":true,...}` 뜨는지 확인

### 1-1) 데이터 보존 설정 ⚠️ 행사에 쓰려면 필수

무료 티어 서버는 **① 무요청 15분이면 잠들고 ② 재시작/재배포 때 프로세스가 새로 뜨며 ③ 영구 디스크가 없습니다.** 아무 설정 없이 쓰면 그때마다 팀 등록·주문·호출 기록이 **전부 사라집니다.** 아래 두 가지를 같이 해두세요. (하나만 해서는 막히지 않습니다.)

**(a) 데이터를 서버 밖에 보관 — 재시작해도 살아남게**

1. [upstash.com](https://upstash.com) 가입 → Redis 데이터베이스 생성 (무료 플랜, 카드 불필요)
2. 대시보드의 **REST API** 항목에서 `UPSTASH_REDIS_REST_URL` 과 `UPSTASH_REDIS_REST_TOKEN` 복사
3. Render 서비스 → Environment 에 아래 환경변수 등록 (토큰은 **코드에 넣지 말고** 반드시 여기에)

   | 이름 | 값 | 필수 |
   |---|---|:--:|
   | `UPSTASH_REDIS_REST_URL` | Upstash에서 복사한 REST URL | ✅ |
   | `UPSTASH_REDIS_REST_TOKEN` | Upstash에서 복사한 REST 토큰 | ✅ |
   | `ADMIN_TOKEN` | 초기화용 비밀 문자열(직접 지정) | 선택 |

4. 재배포 후 `/health` 가 `"persist":{"mode":"redis", ...}` 로 보이면 정상.
   `"mode":"memory"` 면 환경변수가 안 먹은 것이고, `lastError` 에 값이 있으면 연결 실패입니다.

> 환경변수를 비워두면 예전처럼 메모리 전용으로 동작합니다 (로컬 개발용). 코드 수정은 필요 없습니다.

**(b) 서버가 잠들지 않게 — 콜드스타트 지연 방지**

[cron-job.org](https://cron-job.org) 같은 무료 크론 서비스에 아래를 등록합니다. 코드 수정 없음.

- 주소: `https://<서버주소>/health`
- 주기: **10분** (무요청 15분보다 짧아야 함)
- 행사 시작 전날 켜고, 끝나면 끄세요.

**(c) 행사 전 테스트 데이터 초기화**

(a)를 적용하면 테스트 기록도 계속 남습니다. 실서비스 직전에 한 번 비우세요. `ADMIN_TOKEN` 을 설정한 경우에만 동작합니다.

```bash
curl -X POST https://<서버주소>/api/reset -H "Content-Type: application/json" -d "{\"token\":\"<ADMIN_TOKEN>\"}"
```

### 1-2) 슬랙 호출 알림 설정 (선택 — 없어도 나머지 기능은 동작)

관리자 페이지를 켜두지 않아도 담당 마스터 메이트 폰으로 호출 알림이 가게 합니다.

**(a) 슬랙 Incoming Webhook 발급**

1. [api.slack.com/apps](https://api.slack.com/apps) → Create New App → **Blank app**
2. 왼쪽 **Incoming Webhooks** → 활성화 → **Add New Webhook to Workspace**
3. 해커톤 전용 채널을 새로 만들어 지정 (예: `#해커톤-호출-알림`)
4. 발급된 Webhook URL 복사

> 회사 워크스페이스는 앱 설치에 관리자 승인이 필요할 수 있습니다. 승인을 기다리는 동안 개인 워크스페이스를 만들어 URL을 받아 테스트하고, 승인 후 URL만 교체하면 됩니다.

**(b) Render 환경변수 등록**

| 이름 | 값 | 기본값 |
|---|---|---|
| `SLACK_WEBHOOK_URL` | (a)에서 받은 Webhook URL. **없으면 알림 기능 전체가 꺼짐** | 없음 |
| `SLACK_LEAD_USER_ID` | 호출 전반을 관리하는 운영 총괄의 슬랙 멤버 ID | 없음 |
| `ALERT_UNCLAIMED_MIN` | 이 시간(분) 넘게 미처리면 채널에 공개 | 5 |
| `ALERT_LEAD_MIN` | 이 시간(분) 넘게 미처리면 운영 총괄에게 알림 | 10 |
| `ALERT_LEAD_REPEAT_MIN` | 운영 총괄 재알림 간격(분) | 10 |

**(c) 담당자별 슬랙 멤버 ID 채우기**

`config.js`의 `COACH_ASSIGNMENTS` 각 항목에 `slackUserId`를 넣으면 그 사람만 멘션되어 **개인 알림**을 받습니다.

```js
{ id: 'coach-1', name: '김OO', teamNumbers: [1, 2, 3], slackUserId: 'U01ABCDEF' },
```

- 멤버 ID 확인: 슬랙에서 해당 인원 프로필 → 더보기(`⋯`) → **멤버 ID 복사**
- `slackUserId`가 비어 있으면 멘션 없이 이름만 표기됩니다 (채널 알림으로만 전달) — 명단이 확정되기 전에도 동작합니다.

**(d) 알림 단계**

| 시점 | 슬랙에 뜨는 것 | 개인 알림 대상 |
|---|---|---|
| 호출 즉시 | `🔔 팀 47 호출 · 담당 @김OO` + 사유 | 담당 메이트 1명 |
| `ALERT_UNCLAIMED_MIN` 경과 | `⏳ 팀 47 6분째 미처리 — 여유 있는 분이 받아주세요` | 없음(채널에만 노출) |
| `ALERT_LEAD_MIN` 경과 | `🚨 @총괄 장시간 미처리 호출 2건` (묶음) | 운영 총괄 1명 |
| 처리 시작·완료 | 보내지 않음 | — |

- 담당자가 배정되지 않은 팀은 처음부터 멘션 없이 채널에 공개됩니다.
- 같은 호출에 같은 알림은 다시 가지 않으며, 발송 이력을 원격 저장소에 남겨 **서버가 재시작돼도 재발송되지 않습니다.**
- 정상 동작 확인: `/health` 의 `"slack":{"enabled":true, ... "lastError":null}`

> Incoming Webhook은 보낸 메시지의 식별자를 돌려주지 않아 **스레드 답글·이모지 반응·버튼을 쓸 수 없습니다.** 그 기능들은 봇 토큰(승인 문턱이 더 높음)이 필요합니다. 현재 설계는 "호출됐다"는 신호만 전달하고, 처리 상태는 관리자 화면에서 확인하는 방식입니다.

### 2) 두 앱의 config.js에 API 주소 반영

`participant-app/src/config.js`, `admin-app/src/config.js` **양쪽 다** 아래 값을 1)에서 받은 주소로 변경:

```js
export const API_BASE_URL = 'https://hackathon-api-hi55.onrender.com'
```

### 3) 참가자 앱 / 관리자 앱을 각각 배포

Vercel/Netlify 등에 `participant-app`, `admin-app`을 **각각 별도 프로젝트**로 배포 (build: `npm run build`, output: `dist`). 두 앱 모두 1)의 같은 API 서버를 바라보므로, 서로 다른 도메인이어도 데이터가 공유됩니다.

### 4~5) 앱 재배포 & 왕복 테스트

Vercel이 GitHub과 연동돼 있으면 푸시 시 자동 재배포됩니다. 배포 완료 후:

1. 참가자 앱에서 팀 하나 등록 → 마스터 메이트 호출 (사유 작성)
2. 관리자 앱 **호출 알림** 탭에서 그 호출과 사유가 보이는지 확인
3. 처리 시작 → 완료까지 눌러보고, 참가자 화면 상태가 따라 바뀌는지 확인

보이지 않으면 브라우저 개발자도구 Network에서 요청 주소가 `hackathon-api-hi55`인지 확인하세요. 옛 주소면 재배포가 안 된 것입니다.

### 6) 슬립 방지 크론

[cron-job.org](https://cron-job.org) 등에 아래를 등록합니다. 코드 수정은 필요 없습니다.

- 주소: `https://hackathon-api-hi55.onrender.com/health`
- 주기: **10분** (무요청 15분보다 짧아야 함)

### 7) 재시작 후 데이터 생존 확인

가장 중요한 검증입니다. 이게 통과해야 행사 중 데이터 소멸 위험이 사라집니다.

1. 참가자 앱으로 팀 하나 등록 (또는 `/health`의 `keys` 값을 기억)
2. Render → 해당 서비스 → **Manual Deploy** (또는 Restart)
3. 배포 로그의 `[persist] 복원 완료 — N개 키` 에서 **N이 0이 아니면 성공**
4. `/health`의 `keys` 값이 재시작 전과 같은지 확인

`복원 완료 — 0개 키` 가 뜨면 영속화가 동작하지 않는 것이니 환경변수를 다시 확인하세요.

### 8) 구 서비스 삭제

`hackathon-service-6uf0.onrender.com` 는 다른 계정(개인 GitHub 로그인)에 남아 있는 이전 배포입니다. 같은 저장소에 연결돼 있어 푸시할 때마다 자동 배포가 계속 돌아갑니다. **동작에 해는 없지만 어느 서버가 실제 운영본인지 혼동을 유발하므로** 해당 계정으로 로그인해 삭제하세요.

### 10~11) 슬랙 알림 활성화

코드는 이미 들어가 있고, **환경변수 `SLACK_WEBHOOK_URL` 하나만 등록하면 켜집니다.** 설정 방법은 위 **1-2)** 를 보세요. 미등록 상태에서는 알림만 꺼진 채로 나머지 기능이 정상 동작합니다.


## 🧪 로컬 개발/연동 테스트

Node.js 18+ 필요.

```powershell
# 1) 공유 API 서버 (터미널 1)
cd shared-api ; npm run start   # http://localhost:3001

# 2) 참가자/관리자 앱 — 각 config.js의 API_BASE_URL을 http://localhost:3001 로 설정 후
cd participant-app ; npm install ; npm run dev   # http://localhost:5173/
cd admin-app       ; npm install ; npm run dev   # http://localhost:5174/
```

`API_BASE_URL`을 채우면 5173/5174처럼 **포트(origin)가 달라도** shared-api를 통해 실제로 데이터가 공유됩니다 (Vercel에 각각 배포했을 때와 동일한 상황을 로컬에서 재현). `API_BASE_URL`을 비워두면 `localStorage` 폴백만 쓰므로, 같은 브라우저의 두 탭이라도 무관하게 동작 — 이 경우는 아래처럼 같은 origin으로 묶어서 봐야 합니다.

```powershell
# API 서버 없이 UI만 빠르게 훑어볼 때 (같은 origin으로 묶어서 localStorage 공유)
cd participant-app ; npm run build
cd ../admin-app    ; npm run build
cd ..              ; node preview-server.js
# → http://localhost:4173/participant/
# → http://localhost:4173/admin/
```

## 🕐 시간 시뮬레이션 (개발/시연용)

행사 일정(2026-09-21~22) 밖에서도 테스트할 수 있도록 URL에 `?now=` 파라미터를 지원합니다.

```
/participant/?now=2026-09-21T14:30   ← 저녁 주문 시간대로 시뮬레이션
/admin/?now=2026-09-21T17:30         ← 저녁+야식 내역 겹침 구간
```

오프셋 방식이라 카운트다운/시간 흐름도 정상 동작합니다. 파라미터가 없으면 실제 현재 시각을 사용합니다.

## 구현된 기능 요약

**참가자**: 공통 QR → 팀 등록(팀번호·인원수·알러지, 계열사 선택 없음) · 이용 안내 섹션 · 시간대 자동 전환 단일 화면 · 마감 카운트다운 · 음식/음료 카테고리 + 식이 뱃지 + 사진 자리 · **인원수만큼 음식 수량 제한** · 품절 반영 · 주문 수정/취소 + 하단 고정 요약바 · 주문 내역 노출 규칙(orderStart~eatAt, 겹침 표시) · 코치 호출(사유 선택, 팀 번호 기준 담당 조 안내, 상태 표시 + 진동, 횟수 제한) · 시간대별 다크모드

**관리자**: 이름 + 담당 조 입장 · 팀별 주문(담당 조·인원수·과다 표시) + 시간대 필터 + **팀 번호 검색** · 메뉴별 합산 집계 · **알러지 현황 패널** · 품절 토글 · CSV 내보내기(담당 조·인원수 포함) · 호출 알림(사운드/진동, 담당 조 강조 + "우리 조만" 필터, 대기중→처리중→완료, 예상 처리시간) · **코치 현황(조별 대기/대응 상태, 전원 대응 시 경고)** · 통계 대시보드 · 자동 폴링 + 수동 새로고침

**공통**: 서로 다른 origin 간 `shared-api` 통한 실시간 연동 · 서버 통신 실패 시 무음 폴백이 아닌 명확한 오류 알림/배너
